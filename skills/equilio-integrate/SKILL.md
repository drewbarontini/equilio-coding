# Integrate

Start with the available issue, local Markdown, code, PR, or deployed result; the earlier skills need not have run. An ordinary change may use one issue; where a broader problem has an optional parent, use the linked delivery issue as the source of truth for this slice. Review the entire functioning slice through the five [Development Principles](https://github.com/drewbarontini/equilio-coding/blob/main/references/development-principles.md): confirm it still solves the framed problem (**Understand First**), uses the smallest coherent functioning change (**Fewest Changes**), reads clearly (**Optimize for the Reader**), leaves touched areas at least as healthy (**Better Than Before**), and has been verified as integrated behavior (**Close the Loop**). Use these as judgment lenses, not a required output checklist. Run checks proportionate to the change and verify integrated behavior in the running product when feasible, not only its individual components. Record findings and any refinements in local Markdown.

Under **Optimize for the Reader**, check that comments remain accurate and useful, preserve important non-obvious constraints, and introduce no unnecessary narration. Under **Close the Loop**, consider whether new or changed tests add meaningful confidence, assert behavior where practical, and avoid misleading, redundant, brittle, or stale assumptions. These are lightweight review lenses, not a required comment/test audit section.

Update diagrams and durable documentation when the system actually changed and those artifacts will help future work. If review uncovers a material gap in the problem, system understanding, direction, or intended behavior, reconcile that finding and recommend the appropriate earlier skill before claiming review readiness. Before creating a PR, re-read and rewrite the delivery issue body under the [issue write-back contract](https://github.com/drewbarontini/equilio-coding/blob/main/references/issue.md#issue-write-back-contract). Reconcile its claims with actual code and verified behavior: what mattered, what was learned and decided, what behavior now exists, what was checked, and what remains open. Prepare a PR that normally advances one delivery issue, using **Summary** (two or three plain-language sentences on the implemented outcome), **Implementation** (how the code realizes it), **Verification** (what was checked), optional **Callouts** (only useful reviewer focus, unusual choices, tradeoffs, compatibility concerns, or follow-ups), and **Context** (a link to the issue). Keep review-specific code detail in the PR; link to the issue for current understanding rather than copying its lifecycle or a parent's narrative. Use issue-closing syntax only when merge also completes the team's live verification.

The delivery issue is the current account of the work through delivery, in GitHub, Linear, or local Markdown. Establish its destination before any remote update. Refine its narrative and link to code, diagrams, durable docs, PR, and release as available. Record what was released, to whom, what feedback or observation is available, and what remains unknown. When feasible, release to an appropriate audience and use feedback to shape the next slice. Mark the issue live only when the software is actually live; distinguish implemented, merged, deployed, and verified live. Keep planned feedback, observed feedback, and inferences distinct; never invent responses or claim a later state without evidence.

Before finishing, re-read and rewrite the delivery issue body again against the actual code, verified behavior, and any PR, release, review, or feedback learning. Remove stale assumptions, duplicated history, transient implementation detail, and contradictions. Preserve decisions, reasons, risks, and deferred questions in a clean current synthesis so a human or AI can continue from the issue alone.

After reconciliation, re-read the resulting issue and apply the shared [next-operation guidance](https://github.com/drewbarontini/equilio-coding/blob/main/references/issue.md#choose-the-next-useful-operation) using current repository, implementation, verification, and Development Principles evidence. **Follow the understanding, not the sequence.** Finish with one concise **Recommended next:** `<skill or action>` and **Why:** `<reason>`. Recommend human review or stop / complete when the implementation is coherent, sufficiently verified, and accurately represented by the issue; recommend optional Explain only when review-ready work meaningfully changes the maintainer's mental model. Return to the appropriate earlier skill for material problems instead of declaring completion. Skip satisfied concerns and honor explicit skill requests before recommending continuation.
