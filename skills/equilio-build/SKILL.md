# Build

Establish the current state from the request, shared issue, local Markdown, prototype, and code; previous Equilio Coding skills are optional. Apply the five [Development Principles](https://github.com/drewbarontini/equilio-coding/blob/main/references/development-principles.md) throughout Build. **Understand First**: inspect relevant product behavior, code paths, tests, and conventions before modifying them, and distinguish facts from assumptions. Build requires enough understanding of the problem, system, and direction for a responsible, coherent change, not certainty or proof that earlier skills ran. Follow the chosen direction, resolving gaps that materially affect implementation. An ordinary change may have one issue; for a broader problem, a linked delivery issue owns this slice's lifecycle and an optional parent holds overall intent. **Fewest Changes**: build the smallest coherent functioning outcome of the delivery issue, through every product and technical layer needed for someone to experience and evaluate it. Avoid unrelated cleanup and speculative abstraction.

Iterate on the running product so behavior, design, and UX work together. Prefer a slice that can be released independently to an appropriate audience when feasible. When new work emerges, decide whether this slice needs it to function or whether it belongs in a linked follow-up; avoid splitting work only by technical layer. If separate foundational work is necessary, state its enabled capability, verification, and supported functioning slice.

**Optimize for the Reader** and **Better Than Before**: follow local conventions, improve naming and structure before compensating with comments, refine prototype shortcuts, and leave touched code at least as coherent as before. Add comments only for understanding the code cannot convey, preserving meaningful reasoning, constraints, and invariants. Avoid routine narration; inspect relevant comments in touched code and correct or remove stale context.

**Close the Loop**: inspect existing coverage and run appropriate checks. Add or update tests when they meaningfully increase confidence in behavior, choosing the smallest useful test surface and avoiding redundant, brittle tests and unnecessary implementation coupling. Reconcile failures against intended behavior and the issue rather than blindly changing implementation or tests. Verify integrated behavior in the running product when feasible; use manual or other verification when automation adds little confidence, recording its limits. Note meaningful implementation findings in local Markdown. If implementation changes the understanding or overturns a prior decision, explain it to the user when consequential and update the delivery issue rather than silently diverging.

The shared issue may be in GitHub, Linear, or local Markdown. Establish its destination before any remote update. Move accepted conclusions and meaningful changes into a concise account with links to detailed artifacts; do not copy working notes wholesale or duplicate a parent's entire narrative. Report what works, what was checked, and what remains unresolved. Describe implementation as implemented, not merged or live; record actual release and feedback only when they occur.

Before finishing, re-read and rewrite the delivery issue body to reflect the behavior now implemented, meaningful technical decisions and their reasons, discovered constraints, system-level callouts, verification status, and unresolved work. Replace stale plans and consolidate prior understanding. Keep changed-file lists, functions, and patch mechanics in working notes when needed; let the code explain implementation. Preserve only technical detail that materially affects lasting understanding in the issue. Leave the issue sufficient for a human or AI to continue without prior conversation. Follow the [issue write-back contract](https://github.com/drewbarontini/equilio-coding/blob/main/references/issue.md#issue-write-back-contract).

After reconciliation, re-read the resulting issue and apply the shared [next-operation guidance](https://github.com/drewbarontini/equilio-coding/blob/main/references/issue.md#choose-the-next-useful-operation) using current repository, implementation, verification, and Development Principles evidence. **Follow the understanding, not the sequence.** Finish with one concise **Recommended next:** `<skill or action>` and **Why:** `<reason>`. Integrate when functioning implementation exists and coherence review and handoff remain; return to Explore if evidence no longer supports the direction, or Map or Frame for material gaps in system or problem understanding. Skip satisfied concerns; human review, optional Explain, or stop / complete may be appropriate. Honor explicit skill requests before recommending continuation.
