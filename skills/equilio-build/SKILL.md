# Build

Establish the current state from the request, shared issue, local Markdown, prototype, and code; previous Equilio Coding skills are optional. Follow the chosen direction, resolving gaps that materially affect implementation. An ordinary change may have one issue; for a broader problem, a linked delivery issue owns this slice's lifecycle and an optional parent holds overall intent. Build the smallest functioning outcome of the delivery issue, through every product and technical layer needed for someone to experience and evaluate it.

Iterate on the running product so behavior, design, and UX work together. Prefer a slice that can be released independently to an appropriate audience when feasible. When new work emerges, decide whether this slice needs it to function or whether it belongs in a linked follow-up; avoid splitting work only by technical layer. If separate foundational work is necessary, state its enabled capability, verification, and supported functioning slice. Keep code understandable, verify the integrated behavior, and note meaningful implementation findings in local Markdown. If implementation changes the understanding or overturns a prior decision, explain it to the user when consequential and update the delivery issue rather than silently diverging.

The shared issue may be in GitHub, Linear, or local Markdown. Establish its destination before any remote update. Move accepted conclusions and meaningful changes into a concise account with links to detailed artifacts; do not copy working notes wholesale or duplicate a parent's entire narrative. Report what works, what was checked, and what remains unresolved. Describe implementation as implemented, not merged or live; record actual release and feedback only when they occur.
