# Equilio Loop

Start from the user's goal, desired outcome, or existing issue. Treat Loop as a **Supporting Skill**, not a core stage. **Loop owns orchestration. The five Core Skills own judgment.** Preserve their responsibilities and canonical conceptual progression: **Frame → Map → Explore → Build → Integrate**. This is progression, not prescription: **Follow the understanding, not the sequence.** Use [Frame](../equilio-frame/SKILL.md), [Map](../equilio-map/SKILL.md), [Explore](../equilio-explore/SKILL.md), [Build](../equilio-build/SKILL.md), and [Integrate](../equilio-integrate/SKILL.md) as the available workflow operations, invoking the selected skill directly when supported or reading and following its current `SKILL.md` otherwise. Read the [Development Principles](https://github.com/drewbarontini/equilio-coding/blob/main/references/development-principles.md) and apply them throughout. If a required skill or reference is unavailable in the installation, obtain its current repository version before proceeding. If it cannot be obtained, report the missing dependency; do not substitute remembered instructions.

## Establish the shared issue

Inspect the current branch, request, project issue conventions, and relevant existing issues before creating anything. Reuse an issue that clearly owns the goal. Otherwise establish the appropriate delivery issue in the project's issue system; use local Markdown as the issue when that is the project's system or as a draft while preparing a remote issue. An ordinary change can use one issue. For broader work, follow the [parent and delivery issue model](https://github.com/drewbarontini/equilio-coding/blob/main/references/issue.md#one-issue-or-linked-issues) and choose the smallest coherent functioning slice that advances the goal. Do not create a duplicate issue or a large speculative delivery issue.

The issue is the canonical current understanding and the state from which the next useful operation is selected. At every transition, re-read the reconciled issue and relevant current artifacts. Each selected skill owns its issue reconciliation under the [issue write-back contract](https://github.com/drewbarontini/equilio-coding/blob/main/references/issue.md#issue-write-back-contract); Loop reconciles any additional material learning from orchestration before reassessing. Replace stale claims and preserve decisions, reasons, constraints, verification, and open questions. Keep it a concise account of current truth, not a stage log or a substitute for working notes. A future human or AI should be able to make approximately the same routing decision from the issue and evidence without hidden conversation state.

## Choose, run, and reassess

Execution: **Goal / Issue → assess current understanding → choose next skill → run skill → reconcile issue → reassess → repeat**.

Read the issue and relevant repository, implementation, and verification evidence to choose the most useful Core Skill using the shared [next-operation guidance](https://github.com/drewbarontini/equilio-coding/blob/main/references/issue.md#choose-the-next-useful-operation). Start wherever understanding requires attention; skip a skill when its job is already satisfied. Do not require Frame for a well-framed issue, Map for sufficiently understood behavior, or Explore when no meaningful uncertainty remains. Build needs enough understanding for a responsible change, not certainty. If the user explicitly requests a particular skill, run its job first, reconcile the issue, then reassess rather than overriding that intent.

Give the selected skill the current goal, issue, and relevant artifacts; let its current instructions determine depth and methods. Let it perform its job, reconcile the issue, re-read the result, and recommend a next skill or action. Then independently re-read that resulting issue and reassess the recommendation against current evidence before choosing the next operation. Continue until review-ready or meaningful human judgment is required. If those conditions already hold on entry, no Core Skill needs to run. In Loop, stop before Integrate's optional release and live feedback work unless explicitly requested.

Possible routes include **Map → Build → Integrate** for a well-framed issue, **Build → Integrate** for a tiny, obvious change, or **Frame → Explore → Map → Explore → Build → Integrate** for an uncertain interaction that exposes a system constraint. These illustrate adaptive routing; none is a required sequence. Re-enter an earlier skill only when material evidence changes its judgment, such as a wrong problem, unknown constraint, unsupported direction, or missed outcome. Reconcile that evidence and continue toward convergence rather than repeating skills mechanically. If repetition produces no meaningful learning or progress, identify the unresolved question and seek the judgment or evidence needed to proceed. Do not introduce scores, maturity levels, mandatory checklists, routing percentages, or gates between skills.

Make reasonable decisions from repository evidence, the issue, conventions, tests, observed behavior, and the Development Principles. Compare options proportionally, record consequential reasoning, and continue without routine approval gates. Ask for human judgment when an unresolved decision would materially change the goal, product behavior beyond the stated intent, fundamental scope, security or privacy expectations, compatibility guarantees, major architecture, an external commitment, or destructive or irreversible behavior, or when evidence provides no reasonable basis for choosing. Continue independent work while that judgment is pending.

Stop by default at **review-ready**: implementation and appropriate verification complete, the delivery issue reconciled with reality, and the branch and working tree coherent. Commit changes when appropriate for the environment and prepare a PR synopsis or a draft PR when the normal workflow supports it and the request implies it. When preparing a PR, read and follow the same canonical [PR guidance](https://github.com/drewbarontini/equilio-coding/blob/main/references/pull-request.md) as Integrate: **Summary → Callouts → Context**, omitting unnecessary Callouts. Detailed understanding accumulated during autonomous work belongs in the reconciled issue; running the entire workflow does not justify a longer PR. Check whether another functioning slice is required to satisfy the goal; use linked delivery issues when broader work remains. Do not merge, release, deploy, or claim live validation unless explicitly requested and supported by evidence.

## Support human understanding

When work is coherent and review-ready, use the Supporting Skill [Explain](../equilio-explain/SKILL.md) when the implementation meaningfully changes the maintainer's model of the system. Follow its current instructions using the same invocation or reading approach as above. Explain is optional, not a sixth core stage or another coherence review; skip it for trivial changes where it adds no value. If used and it finds no meaningful mental-model change, report that concisely.

Leave the human with coherent, verified, review-ready work, a reconciled issue containing the current understanding, and, when useful, a concise Explain response before human review. Re-read the issue after Explain reconciles any durable new understanding; its teaching output should not be copied wholesale into the issue or PR. If explanation exposes a material contradiction, call it out and return to the appropriate Core Skill to resolve it before claiming convergence. Keep Integrate responsible for coherence and verification.

Before finishing, reconcile any remaining material learning and re-read the resulting issue. Finish with **Recommended next:** `<skill or action>` and **Why:** `<brief reason based on current understanding>`, usually human review, stop / complete, or the specific human judgment needed. Do not produce a routing report or leave the reason only in chat.
