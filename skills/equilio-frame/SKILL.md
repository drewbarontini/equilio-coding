# Frame

Turn an initial signal into an issue-ready account of the problem. Read the request and available issue, local files, prototype, or code first. Use what they already answer; match the depth to the work's impact and uncertainty.

Interview thoughtfully: ask one substantive question at a time, then use the answer to choose the next. Do not run a fixed questionnaire or repeat what the context establishes. Clarify what happens, who is affected, why it matters, what evidence exists, and what improvement would look like. Probe consequential constraints and uncertainty. Challenge a proposed solution when the problem beneath it is unclear. Briefly reflect a materially changed understanding and invite correction. Stop when the problem is clear enough for a useful next move; a small fix may need no questions.

Write a local Markdown draft the user can inspect before creating or materially updating a shared issue. Keep it readable as an emerging issue, not a questionnaire with empty sections. If an issue exists, draft against it and preserve its useful history and links. Follow the project's issue conventions and establish the destination before any remote change. Bring consequential framing to the user for review when appropriate, without making every small edit a gate.

Leave a clear problem, desired outcome, known evidence, constraints, and questions that could change the next move. Record a proposed solution as a proposal; keep viable design choices open for later testing. Distinguish observations, assumptions, and decisions when it matters. Carry accepted conclusions into the shared issue in prose rather than copying the whole draft. If work stays local, the Markdown issue itself can be the shared account.

Notice possible delivery slices without forcing a breakdown before the problem is understood. For a broader problem, a parent issue may hold the shared intent, exploration, and outcome; linked delivery issues can later hold each functioning change. An ordinary change can remain one issue. Keep the question of what someone can experience and evaluate in view, but leave uncertain solution and slice choices open for Map and Explore.

Before finishing, re-read and rewrite the shared issue body to reflect all material framing. Update stale assumptions, preserve meaningful decisions and deferred questions, and leave enough context for Map to continue from the issue. Follow the [issue write-back contract](https://github.com/drewbarontini/equilio-coding/blob/main/references/issue.md#issue-write-back-contract).
