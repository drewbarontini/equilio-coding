# Map

Start from the current request, issue, local Markdown, prototype, or code. Observe the relevant product behavior and inspect the actual code before describing how it works. Follow the paths that matter to the change: entry points, state, data, interfaces, dependencies, tests, and affected surfaces. Scale the map to the task.

Create a local Markdown map that lets another person find the important code and understand the current behavior. Identify boundaries, constraints, decisions that could change the approach, and unresolved questions. Separate verified facts from inferences; use file links or paths precise enough to revisit.

Find the project's shared issue in GitHub, Linear, or local Markdown and carry the map's accepted conclusions into it when ready. The issue should be a readable map and narrative with links to detail, not a pasted file inventory. Establish the remote destination before changing it. Leave enough context for a fresh session to choose a direction without treating uncertainties as resolved.
