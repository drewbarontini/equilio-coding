# Contributing

Keep Equilio Coding small and usable across projects and issue systems.

- Keep exactly five standalone **Core Skills**, in this order: **Frame → Map → Explore → Build → Integrate** (`equilio-frame`, `equilio-map`, `equilio-explore`, `equilio-build`, `equilio-integrate`). Each needs valid `name` and `description` frontmatter, a distinct trigger, one primary job, and a useful output. Each must work when installed alone and entered from a rough request, an issue, a local file, a prototype, or code.
- Keep **Supporting Skills** separate and optional. **Core skills define the workflow. Supporting skills compose, inspect, or extend the workflow without redefining it.** They must not become implicit stages, alter core responsibilities or order, or duplicate a Core Skill's job. Add one only for a genuine recurring, independently invokable atomic job; do not create skills for symmetry or impose a fixed supporting count. Keep category, description, and trigger guidance consistent across the README and skill instructions.
- **Loop owns orchestration.** Keep `equilio-loop` as a Supporting Skill, used with all five Core Skills. Loop accepts a goal, establishes or reuses the right issue, coordinates the current canonical skill instructions, and stops at coherent, verified, review-ready work by default. It must not duplicate the core skills' judgment or methods.
- **Explain owns human comprehension of meaningful system changes.** Keep `equilio-explain` as a Supporting Skill usable independently of Loop or after the core workflow converges. Teach changes in concepts, boundaries, invariants, flows, durable decisions, assumptions, dependencies, and extension points when relevant; filter routine detail rather than summarizing a diff. Skip optional Explain for trivial changes where it adds no value. Integrate retains coherence review; Explain must not become another implementation or review stage.
- Preserve the issue as canonical current understanding and shared memory across Loop transitions, readable by humans and AI without prior conversation. Each Core Skill and Loop must re-read and rewrite it before finishing; Loop must re-read it at each transition. Explain updates an existing issue only for durable new understanding, leaving it unchanged otherwise and creating no competing permanent artifact by default. Write-back is synthesis: replace stale claims, consolidate overlap, and keep material learning and decisions; do not append a stage log or copy the entire Explain output.
- Keep local Markdown available for detailed working notes. Preserve the **Working Notes → Issue → PR** distinction: synthesize understanding into the issue and put patch-specific implementation detail in the PR. Establish a remote destination before changing it. Keep conventions consistent with [the issue reference](references/issue.md) and [PR template](.github/pull_request_template.md). Do not add a stage gate, service dependency, or automation without a demonstrated need.
- Preserve the shared [Development Principles](references/development-principles.md) across Core and Supporting Skills. Link to the reference instead of repeating it; keep its guidance proportionate and leave room for judgment. A small coherent change may still cross every layer required for functioning software.
- Let Loop re-enter earlier skills when material evidence changes their judgment. It should continue autonomously through reasonable choices and ask for human judgment only when a consequential decision lacks a sound basis. Do not add approval gates between skills. Merge, release, and deployment require explicit authorization.
- State what is observed, decided, implemented, merged, deployed, and verified live accurately. Keep the five steps distinct from Equilio's three Models.

Preserve the artifact boundaries: **Issue = durable understanding. PR = implementation-review artifact. Explain output = teaching.** The PR explains how the code changed; Explain teaches what a maintainer should understand differently because it changed. Use the PR and diff as evidence without duplicating them.

Before proposing a change, validate new and modified skills with the skill validator, list the repository through `npx skills add <local-path> --list` when the CLI is available, and confirm that a single Core Skill, Loop, and standalone Explain can each be selected with `--skill <name>`. Read the README, shared references, and example against the actual skill instructions.
