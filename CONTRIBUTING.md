# Contributing

Keep Equilio Coding small and usable across projects and issue systems.

- Keep exactly five standalone **Core Skills**, with the canonical conceptual progression **Frame → Map → Explore → Build → Integrate** (`equilio-frame`, `equilio-map`, `equilio-explore`, `equilio-build`, `equilio-integrate`). This is progression, not a mandatory pipeline: **Follow the understanding, not the sequence.** Each needs valid `name` and `description` frontmatter, a distinct trigger, one primary job, and a useful output. Each must work when installed alone and entered from a rough request, an issue, a local file, a prototype, or code. Honor explicit skill requests rather than overriding them with routing.
- Keep **Supporting Skills** separate and optional. **Core skills define the workflow. Supporting skills compose, inspect, or extend the workflow without redefining it.** They must not become implicit stages, alter core responsibilities or the conceptual progression, or duplicate a Core Skill's job. Add one only for a genuine recurring, independently invokable atomic job; do not create skills for symmetry or impose a fixed supporting count. Adaptive routing is shared behavior across Core Skills and Loop, not a new routing skill. Keep category, description, and trigger guidance consistent across the README and skill instructions.
- **Loop owns adaptive orchestration.** Keep `equilio-loop` as a Supporting Skill, used with all five Core Skills available. Loop accepts a goal or issue, establishes or reuses the right issue, assesses understanding, selects a useful skill, runs its current canonical instructions, lets it reconcile the issue, re-reads the result, and reassesses. It may enter anywhere, skip satisfied concerns, or revisit earlier ones when material evidence requires it. Continue until coherent, verified, review-ready work or meaningful human judgment is required. Do not duplicate the core skills' judgment or methods or default to running every skill.
- **Explain owns human comprehension of meaningful system changes.** Keep `equilio-explain` as a Supporting Skill usable independently of Loop or after the core workflow converges. Teach changes in concepts, boundaries, invariants, flows, durable decisions, assumptions, dependencies, and extension points when relevant; filter routine detail rather than summarizing a diff. Skip optional Explain for trivial changes where it adds no value. Integrate retains coherence review; Explain must not become another implementation or review stage.
- Preserve the issue as canonical current understanding, shared memory, and the basis for selecting the next operation. Each Core Skill performs its job, reconciles the issue, re-reads the resulting issue, then gives one concise **Recommended next:** `<skill or action>` and **Why:** `<reason>`. Base recommendations on that issue, relevant repository evidence, implementation state, verification results, and Development Principles, so a fresh human or AI can reach approximately the same decision without hidden chat context. Human review, optional Explain, or stop / complete are valid recommendations. Keep the shared [selection guidance](references/issue.md#choose-the-next-useful-operation) consistent with the skills instead of duplicating a routing report in each.
- Each Core Skill and Loop must re-read and rewrite the issue before finishing; Loop must re-read it at each transition. Explain updates an existing issue only for durable new understanding, leaving it unchanged otherwise and creating no competing permanent artifact by default. Write-back is synthesis: replace stale claims, consolidate overlap, and keep material learning and decisions; do not append a stage log or copy the entire Explain output.
- Keep local Markdown available for detailed working notes. Preserve the **Working Notes → Issue → PR** distinction: synthesize understanding into the issue and put patch-specific implementation detail in the PR. Establish a remote destination before changing it. Keep conventions consistent with [the issue reference](references/issue.md) and [PR template](.github/pull_request_template.md). Do not add a stage gate, service dependency, or automation without a demonstrated need.
- Preserve the shared [Development Principles](references/development-principles.md) across Core and Supporting Skills. Link to the reference instead of repeating it; keep its guidance proportionate and leave room for judgment. A small coherent change may still cross every layer required for functioning software.
- Keep routing judgment-based. Skip Frame when framing is strong, Map when system understanding is sufficient, and Explore when resolving uncertainty would not change the decision. Build requires enough understanding, not certainty. Re-enter earlier skills only when material evidence requires it; do not create loops merely because they are allowed. Loop should continue autonomously through reasonable choices and ask for human judgment only when a consequential decision lacks a sound basis. Do not introduce completion scores, maturity levels, routing percentages, mandatory checklists, automatic prototypes, formal or approval gates between skills, or requirements to pass every skill. Merge, release, and deployment require explicit authorization.
- State what is observed, decided, implemented, merged, deployed, and verified live accurately. Keep the five steps distinct from Equilio's three Models.

Preserve the artifact boundaries: **Issue = durable understanding. PR = implementation-review artifact. Explain output = teaching.** The PR explains how the code changed; Explain teaches what a maintainer should understand differently because it changed. Use the PR and diff as evidence without duplicating them.

Before proposing a change, validate new and modified skills with the skill validator, list the repository through `npx skills add <local-path> --list` when the CLI is available, and confirm that a single Core Skill, Loop, and standalone Explain can each be selected with `--skill <name>`. Read the README, shared references, and example against the actual skill instructions.
